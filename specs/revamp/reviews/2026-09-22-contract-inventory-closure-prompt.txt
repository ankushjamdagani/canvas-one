# RV-02f — Closed command payloads and results

Planning specification, 2026-09-22. This complements [commands/panels](commands-and-panels.md), [transactions](transactions.md) and [storage](storage-and-limits.md). No command is implemented by this document. Unknown commands/fields reject. All referenced records use the closed document schema, not generic JSON patches.

## Context and result boundary

`Id` is UUID, `Hash` is lowercase SHA-256 hex, `Revision` is a nonnegative safe integer. `Empty={}`. `Point={x:number,y:number}` uses finite canvas coordinates within document bounds. `ViewRef={projectId:Id,branchId:Id,viewId:Id}`. `Selection={elementIds:Id[],connectionIds:Id[],groupIds:Id[],noteIds:Id[]}` contains unique IDs belonging to that view/document.

An authored request is `{commandId,operationId:Id,projectId:Id,branchId:Id,expectedWorkingRevision:Revision,actor:Actor,payload}`. Actor is `{actorId:Id,kind:'local-human',displayName:string}`; empty displayName is allowed and rendered “Local user”, never authenticated. Project-scoped commands replace branchId/expectedWorkingRevision with `expectedProjectRevision`; bootstrap create/import has no existing revision. Preference commands use `{expectedPreferenceRevision,payload}`. Navigation/export/run controls are controller requests with explicit context, never persisted as authored operations. A context mismatch rejects rather than silently using whichever branch is currently active.

Result union: `{status:'applied',operationId,projectRevision:Revision,branchRevision:Revision|null,changedIds:Id[],undo:{entryId:Id,label:string}|null,value:CommandValue}`; `{status:'invalid',issues:Issue[]}`; `{status:'stale',scope:'project'|'branch'|'preferences',expected:Revision,actual:Revision}`; `{status:'missing',ids:Id[]}`; `{status:'failed',code:'quota'|'unavailable'|'referenced-artifact'|'operation-id-reused'|'limit'|'ineligible'|'conflict'|'unsupported-version'|'duplicate-version',issues:Issue[]}`. Persist the applied result with the operation receipt. No new durable undo entry is reconstructed on retry/reload; entryId only resolves in the originating live session.

Controller result union is `{status:'done',value:CommandValue}`, `{status:'cancelled'}`, or invalid/stale/missing/failed above. User cancellation is not a failed write. CommandValue is closed: `{kind:'none'}`, `{kind:'project',projectId,branchId}`, `{kind:'branch',branchId}`, `{kind:'artifact',artifactType:'checkpoint'|'commit'|'publication'|'part',id,revision:Revision|null}`, `{kind:'run',runId}`, `{kind:'candidate',candidateId,snapshotId:Hash,conflictIds:Id[]}`, `{kind:'draft',draftId}`, or `{kind:'download',downloadId:Id}`. DownloadId is a local completion receipt, never filesystem access or portable content. Each row below fixes its success value; no arbitrary return bag.

Candidate IDs address immutable controller-owned candidate revisions. Every conflict resolution creates a new candidateId/snapshotId and invalidates the old candidate's eligibility, never mutates a running candidate. A candidate retains expected project/source/main revisions, both heads, merge base and unresolved conflicts. It cannot be accepted from portable input. A resolved candidate may run only when it passes readiness. Reload discards unpublished candidates; branch working copies are unaffected. User can prepare again from durable heads. Superseded candidate IDs return failed/ineligible; unknown or reload-expired IDs return missing. branch.create always validates expectedHeadId for both source choices; head mismatch returns failed/conflict with code HEAD_MOVED in its issues, while revision mismatch returns stale.

Project revision increments on every durable project mutation (including branch writes, metadata, runs, parts and pruning); preferences are separate. Branch commands ordinarily compare only branch revision, then atomically increment the current project revision, avoiding unnecessary conflicts across branches. Rename additionally compares its supplied project revision. Publication compares project/source/main tokens; this conservative policy may require reprepare after unrelated project writes. Saving candidate runs must not itself invalidate the candidate: the candidate's structural token tracks source/main revisions and heads, while publication takes a fresh expected project revision after evidence save. Immutable candidate snapshot and evidence fingerprints remain pinned. Project title is navigation metadata; Document.title is a branch/historical snapshot caption, and switching branches never overwrites project.title.

## Model authoring and selection

Replacements must keep definition IDs. Existing nested IDs remain stable; new members get fresh UUIDs. Missing replace/remove targets, duplicate change targets, unknown IDs/fields and invalid cross-references reject the entire command. At most 1,000 changes, also final-document byte/count limits; reducer validates the complete candidate before persistence. Each user gesture/form Apply is one compound command/undo entry.

Domain intents (add component, draw connection, change settings, scenarios, notes, saved views, drag placements) compile to this boundary through schema-aware adapters. Deletion first previews the complete dependency closure; no implicit cascade outside the confirmed set. Future AI must propose the same typed changes for preview/review and cannot bypass validators, revisions or authorization. # RV-02e — Publication metadata and portable record closure

Planning contract, 2026-09-22. Implements the existing local-publish default in decisions.md. No remote publishing, accounts or automatic version inference.

`PublicationMetadata={version:{major:number,minor:number,patch:number},title:string,rationale:string,ticketUrl:string|null}`. Version components are safe integers 0–999999; title is trimmed 1–80 code points, rationale 0–4000. Ticket URL is null or an absolute http/https URL <=2048 characters, with no username/password; opening it is an explicit external-link action. Author uses Actor from the command envelope; optional display name never changes actor identity or implies authentication.

First proposal defaults to 0.1.0. Subsequent proposal offers major/minor/patch bump of the latest published version, with explicit preview and manual entry. Major resets minor/patch to zero; minor resets patch; patch increments patch. Overflow disables that suggestion. User must choose/confirm the displayed version; graph shape never determines it. No prerelease/build metadata in v1. Display `vM.m.p`; canonical versionKey is `M.m.p` without leading zeros.

Versions strictly increase lexicographically by numeric components compared to the latest publication ordinal. Enforce uniqueness of `[projectId+versionKey]` in the same transaction as ordinal/head updates; concurrent attempts reject stale or duplicate version, never silently bump. Import validates ascending ordinal/version order and uniqueness. A reopened source branch can publish only a new higher version. No reuse, editing or deletion of an individual published version.

Duplicate version returns failed/duplicate-version; a lower nonduplicate version is invalid with issue path metadata.version. Numeric version suggestions are drafts until explicit publication succeeds.

Publication row adds `metadata:PublicationMetadata,versionKey:string` to the storage table. versionKey is derived and validated against metadata, not a second editable field. Message on the merge commit is the publication title; rationale/ticket remain publication metadata. Metadata is included in authored-history export and operation request hashing, excluded from executable scenario fingerprints. Updating a draft title/rationale/version before publish does not require rerunning unchanged executable content; published metadata is immutable. Local timestamps are display data only.

Project row adds `revision:Revision` for project-level CAS. Table record keys are required fields: portable branch/commit/publication/checkpoint/run/part records include id (and part revision); snapshot records include their content-hash id. ProjectBundle arrays omit repeated projectId because the enclosing project owns their namespace; import supplies projectId on insertion. ProjectBundle additionally includes `createdAt,updatedAt`; project revision/importSourceId are device-local and reset on import (revision=0, importSourceId=source bundle id). All portable run traceState values are `not-saved` because chunks are excluded; conversion never alters checks/status/summary/manifest.

The initial snapshot is the project's actual creation content (blank or selected template), not necessarily an empty document. It remains immutable and pinned. Initial main/draft share it; imports preserve their declared initialSnapshotId. An unborn branch's ancestry is that creation snapshot. A fork from an existing head keeps the head even when copying its uncommitted working snapshot.

Portable records preserve actor metadata, authoring timestamps and immutable history. Imports do not preserve local trust, revision counters, operation receipts or session handles. Those transformations occur only in repository fields; authored Document bytes and snapshot IDs stay unchanged. Projects always export from one consistent readonly transaction; precomputed bytes correspond to that captured revision.

Acceptance: version collisions and concurrent publish; 0.1.0 initial proposal; manual numeric version ordering (0.10.0 > 0.9.9); overflow; hostile URL schemes; absent author display; metadata-only edits reuse executable evidence; import/export record-key/reference inventory; immutable publication; project create/import retry identity and project/branch CAS races.

ARTIFACT reviews/2026-09-22-contract-inventory-report.md
**Verdict: REVISE** — 6 correctness/implementability gaps, 5 minor ambiguities.

---

## Critical gaps

### C1. `history.publish` missing `expectedProjectRevision`

**transactions.md** explicitly states: *"publication takes a fresh expected project revision after evidence save"* — meaning the candidate's structural token intentionally omits project revision (so run saves don't stale it), and publish must supply one separately.

But the payload is `{candidateId,publicationId,mergeCommitId,metadata,evidence,keepSourceOpen}` — no `expectedProjectRevision`.

**Fix:** Add `expectedProjectRevision:Revision` to the `history.publish` payload. This is the project revision read *after* evidence is saved, distinct from the prepare-time token inside the candidate.

---

### C2. `project.rename` envelope is undefined

Table says *"plus project revision in branch envelope."* The branch envelope is `{commandId,operationId,projectId,branchId,expectedWorkingRevision,actor,payload}`. The project-scoped envelope replaces branch fields with `expectedProjectRevision`. A hybrid (both `expectedWorkingRevision` and `expectedProjectRevision`) is neither defined nor valid by the context boundary.

transactions.md confirms rename compares its project revision in addition to the normal branch revision check, but gives no envelope form for this.

**Fix:** Either (a) define a combined envelope `{…branchFields,expectedProjectRevision:Revision}` explicitly for this command, or (b) put `expectedProjectRevision:Revision` in the payload alongside `title:string` and document that this command uses branch envelope + extended payload. Pick one and close it.

---

### C3. `EvidenceRef` type undefined

Both `history.commit` and `history.publish` take `evidence:EvidenceRef[]`. The type never appears in any of the three contracts. The all-scenario-pass rule requires the server to match evidence to configured scenarios, which requires knowing the `EvidenceRef` schema.

**Fix:** Close `EvidenceRef` — minimally `{scenarioId:Id,runId:Id,snapshotId:Hash}`. Add to the "Context and result boundary" type glossary.

---

### C4. `dependencyPreviewId` has no generating command

`selection.delete` and `part.capture` consume a `dependencyPreviewId` that *"binds exact branch revision and enumerated removal/reference repairs."* No registry entry produces this token. It's neither an authored command result nor a defined controller result kind (`draft`, `candidate`, `run`, `download` — not a dependency preview token).

**Fix:** Either (a) add a controller command `selection.preview-delete → {kind:'dependencyPreview',dependencyPreviewId:Id,boundRevision:Revision,removals:Id[],repairs:Id[]}` to the controller result union and register it, or (b) state explicitly that this is a local UI token computed in the adapter layer, define its schema, and document the failure code when stale (`failed[stale-token]` or extend `stale` to cover it).

---

### C5. Restore-into-main contradiction

`command-inventory.md`: *"Main direct commits and restore into main are disabled."*

`transactions.md` history table: *"Restore affects only a working draft, not published history"* — with no mention of main being forbidden.

These contradict. One contract permits restore-into-main-working-draft; the other forbids it entirely.

**Fix:** transactions.md must add an explicit row precondition or footnote: *"restore into main branch rejects; caller must branch.create(source=working) then switch."* Both contracts must agree.

---

### C6. No failure code for duplicate version key

`publication-metadata.md`: *"Enforce uniqueness of [projectId+versionKey] in the same transaction … concurrent attempts reject stale or duplicate version."*

The `failed` union codes are: `quota|unavailable|referenced-artifact|operation-id-reused|limit|ineligible|conflict|unsupported-version`. None clearly maps to "version key already exists." `conflict` is the closest but is already used for merge conflicts.

**Fix:** Either map duplicate version key explicitly to `failed[conflict]` in the publication section, or add `'duplicate-version'` to the failure code union. Document which code the consumer should expect for this case.

---

## Implementability ambiguities (REVISE)

### A1. `history.resolve-conflict` — superseded candidateId rejection code unspecified

Each resolution creates a new `candidateId` and *"invalidates the old candidate's eligibility."* But what status does sending a superseded candidateId return? `failed[ineligible]`? `missing`? Consumers need to distinguish "candidate gone" from "candidate structurally wrong."

**Fix:** State that a superseded candidateId returns `failed[ineligible]` and document this in the candidate lifecycle note.

---

### A2. `branch.create` — `expectedHeadId` validation conditionality

For `source:'working'`, the caller pins the current working revision via the branch envelope. `expectedHeadId` also appears in the payload. If a commit occurs between the caller's read and the create, the head advances but working revision is unchanged — `expectedWorkingRevision` would pass, `expectedHeadId` would reject.

Is `expectedHeadId` always validated regardless of `source`? Or only for `source:'head'`?

**Fix:** Explicitly state: "`expectedHeadId` is always validated regardless of `source`; it prevents committing to the wrong ancestry baseline."

---

### A3. `part.capture` — `revision` field is redundant and error-prone

The contract states: *"revision must be `expectedLatestRevision+1`, or `1` when `null`."* The value of `revision` is therefore fully determined by `expectedLatestRevision`. A caller who passes `revision=5, expectedLatestRevision=3` must be rejected, but the rule for that rejection isn't given a failure code.

**Fix:** Either remove `revision` from the payload (server computes it) and return the assigned revision in the `artifact` result value, or keep it and explicitly state that mismatch returns `invalid` with an issues entry on `revision`.

---

### A4. `panel.resize` — clamp vs reject for invalid values ambiguous

*"clamp only interactive geometry, reject invalid persisted records"* — both reach the server via the same `panel.resize` command. The contract gives no way for the command to distinguish interactive from persistence-restore context. If both paths use the same command, one policy must apply uniformly.

**Fix:** State which policy applies to the command boundary: either always clamp (and fix persistence at read time before submitting the command), or always reject out-of-bounds values (and require callers to clamp before issuing the command). Remove the dual-path language from the command table row.

---

### A5. Preference envelope type for zoom/fit/pan commands is implicit

`canvas.zoom-in/zoom-out/fit` write preferences only, meaning they use `{expectedPreferenceRevision,payload}`. But the table mixes them with branch-envelope commands without marking the envelope type. Same applies to `panel.*` commands. Consumers must infer envelope type from the "preferences only" annotation.

**Fix:** Add an envelope-type column or marker to the registry table (e.g., `(pref)` suffix), or explicitly state in the table header: *"rows annotated 'preferences only' use the preference envelope; all others use the branch envelope unless noted."*
