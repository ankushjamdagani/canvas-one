# RV-02d — Document schema and runner boundary

Status: proposed contract, 2026-09-22; requires Claude review. This is a specification, not implemented TypeScript. Implementation remains held. References: [execution fixtures](execution-slices.md), [identity](run-identity.md), [limits](storage-and-limits.md).

## Representation and validation

`studio-model/1` is the new authored schema. Portable container version 9 is separate. Records below are closed: unknown properties/kinds/versions reject, never silently strip. `Id` is a lowercase canonical UUID; constructors generate it, import preserves it. IDs are unique across all independently identified members of one document, including nested members. `Ref` always names an ID of the specified kind. JSON values are finite, plain, bounded and surrogate-valid as in canonical-json-v1. No executable strings, expressions, HTML, credentials or arbitrary extension bag.

Two validation levels share one schema. **Storable** requires correct types/bounds/IDs/references; incomplete behavior is represented explicitly by `unmodeled`, not missing fields. Empty documents, empty scenarios and missing behavior can autosave/checkpoint. **Runnable** additionally requires complete scope, supported executable behavior, compatible ports, nonempty inputs and explicit terminal policy. Readiness errors never prevent preserving a structurally valid incomplete design. Import with dangling references fails before insertion. Deletion is a compound operation with an explicit dependency preview; it removes/replaces affected references atomically or rejects.

| Record | Exact fields (all required unless `?`) |
|---|---|
| Document | `schema:'studio-model/1', id, title, elements:Element[], connections:Connection[], relations:Relation[], schemas:PayloadSchema[], fixtures:Fixture[], refinements:Refinement[], scenarios:Scenario[], views:View[]` |
| Element | `id, label, description, visualKind, ports:Port[], behavior:Behavior` |
| Port | `id, label, direction:'in'|'out', channel:'call'|'message'|'data'|'event', schemaId, responseSchemaId:Id|null` |
| Endpoint | `elementId, portId` |
| Connection | `id, label, kind:'call'|'message'|'data', source:Endpoint, target:Endpoint, config` (discriminated below) |
| Relation | `id, label` and either `{kind:'contains',parentId,childId}`, `{kind:'deployed-on',elementId,hostId}`, or `{kind:'descriptive',sourceId,targetId}` |
| Fixture | `id, schemaId, value:Json` |
| View | `id, label, placements:Placement[], connectionIds:Id[], relationIds:Id[], groups:Group[], notes:Note[]` |
| Placement | `id, elementId, x, y, width, expanded:boolean` |
| Group | `id, label, elementIds:Id[], collapsed:boolean` |
| Note | `id, text, x, y, width, tone:'paper'|'neutral', attachedElementIds:Id[]` |

`visualKind` is exactly the current 29-kind catalog in `src/domain/execution.ts:VALID_KINDS`, plus `state-machine`, `data-pipeline`, `host`. It never selects behavior. One element occurs at most once in a view; view groups are one-level, non-overlapping sets of placed elements. Views can show only connections whose endpoints are placed; notes may attach only to placed elements. View groups are not executable containment. A `contains` relation is an acyclic single-parent forest. `deployed-on` connects a resource element to a host behavior; at most one direct host per resource, no placement inference from drawing geometry. Descriptive relations have no runtime effect. Multiple connections may share elements if ports differ; duplicate `(kind,source port,target port)` rejects. Synchronous call cycles reject; message cycles are allowed only under finite runtime budgets.

Payload schemas are a deliberately small closed grammar: `{id,label,shape}` where shape is `{type:'string'|'boolean'|'number'|'integer',nullable:boolean}`, `{type:'record',nullable,fields:[{id,key,optional:boolean,shape}]}`, or `{type:'list',nullable,items:shape,maxItems}`. An additional scalar-only shape is `{type:'scalar-union',nullable,types:('string'|'boolean'|'number'|'integer')[]}` with 2–4 distinct alternatives (number and integer cannot coexist); it explicitly admits mixed external scalar data such as S03's integer/string amount. No record/list unions or union inference. No recursive schema references, coercion or prototype keys (`__proto__`, `prototype`, `constructor`). Record keys are unique, unknown payload fields reject. Number means finite double; integer means safe integer. Nullable is explicit, missing optional fields differ from null. Port compatibility requires identical normalized shapes (ignoring field IDs/labels and sorting record fields by key), not merely equal display names. Call ports require a non-null response schema; other channels require null. Call responses reuse their initiating correlation, not a second authored reverse edge.

## Closed behavior vocabulary

Every behavior has `kind` and `version:1`. No implicit behavior derives from an icon. A resource profile is explicit; logical behavior alone has no capacity metric.

| Kind | Additional fields and semantics |
|---|---|
| `unmodeled` | `reason:string`; legal to store, cannot be reached in a runnable scenario except behind an explicit boundary fixture |
| `resource` | `config:ResourceConfig`; six retained resource variants below |
| `machine` | `states:[{id,label}], initialStateId, contextSchemaId, initialContextFixtureId, transitions:Transition[]`; transitions ordered, first matching rule wins |
| `pipeline` | `inputSchemaId, outputSchemaId, errorSchemaId, operations:Operation[]`; ordered operations, each row keeps immutable input row identity |
| `decision` | `inputSchemaId, cases:[{id,guard,outputPortId,value:Value}], fallback:{outputPortId,value:Value}`; ordered first matching case, exactly one output |
| `host` | no additional fields; availability comes from scenario fault schedule |

`ResourceConfig` is a copied, versioned schema contract, not an import of a legacy runtime type: common `capacity, concurrency, queueLimit, failureRate, maxRetries, retryDelayMs`; variant `type:'source'|'processor'`, `type:'storage',writeCapacity`, `type:'router',strategy:'round-robin'|'weighted'|'conditional'`, `type:'cache',mode:'fixed'|'lru',hitRate,entries,ttlMs`, or `type:'broker',delivery:'competing'|'broadcast'`. Preserve current numeric validation ranges and exact semantics in `src/domain/execution.ts:validateBehavior`; `failureRate`/`hitRate` are percentages, capacity is work units per second per slot, retries exclude initial attempt. These fields all enter identity even when an individual retained variant currently ignores one. Removing redundant fields is a later version change, not an implementer cleanup.

Connection config: `data` has `{}`. `call` has `{latencyMs,returnLatencyMs,weight,condition:RouteCondition|null,fallback:boolean,resource:ResourceCallMetadata|null}`. `message` has `{latencyMs,ackDelayMs,messageTtlMs,weight,condition:RouteCondition|null,fallback:boolean,resource:ResourceCallMetadata|null}`. RouteCondition is `{field:'class'|'operation'|'tag',value:string}`; class uses stable class ID. Preserve current edge numeric ranges; weight must additionally be <=1e6 to bound normalized sums. Retained outgoing selection order is stable edge ID order. Behavioral connection configs are timed only; logical runners use their routing conditions but produce no synthetic delay measurements.

`Path` is an array of literal record keys or nonnegative integer list indices, never a dotted executable expression. `Value` is `{kind:'literal',value:Json}`, `{kind:'read',source:'input'|'context',path:Path}`, `{kind:'record',fields:[{key:string,value:Value}]}`, or `{kind:'list',items:Value[]}`. Constructor keys are unique and schema validated; all expression depth/node budgets apply. These constructors allow request payloads containing newly assigned IDs without executable strings. Missing reads produce a typed missing value (only `exists` can test it); assignment of missing to a required target is a modeled error, not undefined JSON.

Guard grammar: `{op:'equals'|'notEquals',left:Value,right:Value}`, `{op:'exists',value:Value}`, `{op:'all'|'any',guards:Guard[]}`, `{op:'positiveInteger',value:Value}`, `{op:'nonEmpty',value:Value}`, `{op:'every',value:Value,itemGuard:Guard}`. Within `every`, `input` is the current item and `context` stays machine context. Arrays/objects compare by canonical JSON; primitive comparisons have no coercion. `all`/`any` require nonempty operands. `every` on empty input is true, so valid-cart uses both `nonEmpty` and `every`. Wrong operand types reject readiness when statically knowable, otherwise trace a modeled validation error. Depth/count limits apply to the entire expression tree.

Transition: `{id,fromStateId,eventPortId,guard:Guard|null,toStateId,effects:Effect[]}`. Effects are `{id,kind:'assign',path:Path,value:Value}`, `{id,kind:'request-id',path:Path}`, `{id,kind:'emit',portId,value:Value,correlation:{kind:'current'}|{kind:'context-request',path:Path}}`, or `{id,kind:'trace',code:string}`. Apply effects in order to a copied context; validate final context/emissions atomically before changing state or emitting anything. Request IDs derive from run-local root ID and a monotonic invocation counter, not wall clock/RNG. Active request ID must be read explicitly by guards; stale response policy in S01 is modeled using these rules. Event payload includes the response request ID as an explicit schema field. No hidden checkout-specific interpreter.

Operation has stable `id` and one of: `validate {schemaId}`, `trim {path}`, `map {fields:[{id,targetKey,value:Value}]}`, `filter {guard}`, `deduplicate {path}`, `group-sum {keyPath,valuePath,keyName,sumName}`. All operations preserve row provenance; filter exclusion and duplicates are explicit outcomes. `map` reads row as input, context is empty record; no overwriting duplicate target keys. `group-sum` requires string keys and safe integer amounts, checks each addition for overflow, sorts keys by UTF-16 code units. Validation errors route original row/provenance to the error output. A non-validation operation with wrong input type produces an explicit row error; it cannot silently coerce/drop. Whole-pipeline schema validation covers output and error ports.

## Scenarios, assertions and refinements

### Explicit emission and response wiring

Additional closed behavior fields required by the rows above: machine `responseBindings:[{id,callPortId,eventPortId}]`; pipeline `inputPortId,outputPortId,errorPortId`; decision `inputPortId`; resource `entryPortId`. Decision entry is an inbound data port with shape equal to inputSchemaId; all case/fallback ports are outbound data ports and each emitted value must satisfy its port schema. A machine binding maps an outbound call port to an inbound event port on the same machine; exactly one binding per outbound call port, compatible response/event shape. The bridge delivers the response payload to that event port with the original request correlation, never by guessing a port name. Resource entryPortId is an inbound call/message port; every retained resource outgoing edge names an explicit outbound port and the target's declared entry port. Multiple ports are legal but selected routes are explicit edges, never inferred from drawing order. Pipelines require matching data input/output/error ports. Host/unmodeled have no runtime dispatch.

Call-frame identity and application request identity are distinct. Every call creates a system-owned frame ID used exclusively to settle and route its response; authored effects cannot replace it. `emit.correlation` selects the application request ID in invocation metadata (current or explicit context path), never the frame ID, and never inserts a payload field. Authors construct the payload field explicitly. When a machine guard reads response `requestId`, both the call response schema and bound event schema must declare that field with identical shape; the responder must return it explicitly. No post-validation field injection occurs. Request IDs generated by request-id remain stable within one run; fixtures reference prior emissions using the explicit binding rules below rather than guessing generated strings.

Effects additionally include `{id,kind:'reply',value:Value,outcome:'succeeded'|'rejected'|'failed'|'expired'}` and `{id,kind:'schedule-event',delayMs,eventPortId,value:Value}`. Reply settles the current initiating call frame exactly once and returns its typed response; invalid double reply fails the run. Async emissions use separate message roots linked to the call root. A scheduled event is a declared timer effect in timed mode; delay is finite 0..600000ms, target an inbound event port on the same element. In logical mode the timer is not scheduled and the trace records `timer-awaits-explicit-input`; the fixture must provide the corresponding timeout if that path is exercised. Late timeout/response carries its request ID in payload; S01's active-request guard ignores stale ones. No wall-clock timer drives modeled completion.

Each invocation carries an immutable call-frame ID, root/journey IDs, request ID, parent event ID and payload reference. `correlation:{kind:'context-request',path}` reads a nonempty string request ID after prior effects; missing/null is a modeled error. Values constructing emissions/replies are validated against the target/output schema. State machines atomically apply one transition per dispatched event, with explicit trace-only self-transitions for ignored duplicates/stale replies. Decision selects one output, preserving invocation context; pipeline processes the input list and emits ordered success/error arrays with provenance. Data connections forward the invocation context unchanged; call creates a child call frame; message creates a linked message root. Reply may originate in a descendant reached through data edges and resolves the still-open initiating frame. A resource completion emits unchanged payload on its selected continuation routes; terminal resources return unchanged payload as response, with separate transport outcome. Business outcomes require explicit decision/reply behavior, not interpretation of aggregate success counters.

S02 composition uses validate pipeline/decision → payment decision → accepted/rejected reply machine; accepted transition emits a fulfillment message and a reply in declared order. Payment outcome is explicit typed fixture input; a timeout fixture yields an expired reply. Resource profiles are separate resource elements on declared call paths. No automatic business retry, implicit payment service or hidden checkout-specific operation is introduced. Readiness rejects unbound call responses, double-reply-capable sequential effect lists, mismatched schemas and missing pipeline outputs. Runtime catches path-dependent double settlement or budget-exhausting message cycles as failed/incomplete evidence.

Scenario fields: `id,label,revision,mode:'logical'|'timed',scopeElementIds:Id[],entryPorts:Endpoint[],inputs:Input[],workloads:Workload[],faults:Fault[],boundaries:Boundary[],refinementSelections:Selection[],initialContexts:[{elementId,fixtureId}],assertions:Assertion[],seed,budgets,completion,assumptions:Assumption[]`. Revision is a nonnegative safe integer incremented on any scenario edit, including label; projections exclude label but include revision (conservative invalidation). There is no scenario enabled/required flag. Workload enablement remains supported inside a scenario and cannot disable its verification requirement.

Input: `{id,entry:Endpoint,fixtureId,journeyId:Id,atMs:number|null,payloadBindings:InputBinding[],resource:ResourceMetadata|null}`; array order is semantic. InputBinding is `{targetPath:Path,source:{port:Endpoint,journeyId:Id,occurrence:number,path:Path}}`: read an earlier emission's payload in the same run, with zero-based occurrence among emissions at that port/journey in scheduler order. Sources must already exist when consumed; forward/missing references are modeled input errors, never waits or guessed values. Bindings read the original source values and replace distinct non-overlapping existing target paths in a cloned fixture, then validate the entire payload before dispatch. The fixture itself must be schema-valid (a string placeholder can be replaced by a generated string ID). Bindings and their source references enter the executable projection. S01 can therefore inject a late response using occurrence 0 after occurrence 1 was emitted. Such external events are explicit scenario inputs, not fabricated settlements of the original call frame.

ResourceMetadata is `{requestClassId:Id,operation:'read'|'write',key:string|null,tags:string[],deadlineMs:number}`; class ID is a scenario-local classification token, not a required workload-class reference; deadlineMs is an absolute modeled timestamp greater than input time. A finite input directly targeting a resource requires this metadata; other finite inputs require null. For call/message connections from non-resource behavior into a resource, config.resource requires ResourceCallMetadata: `{requestClassId:Id,operation:'read'|'write',key:string|null,tags:string[],deadlineDurationMs:number}`. Duration must be positive and <=600000; the adapter computes the absolute deadline at admission. Connections between resources inherit invocation metadata and require null, as do connections to non-resource targets. No absolute/relative timestamp field is overloaded. Resource routing does not infer class/operation/key/tags from payload property names. Logical scenarios reaching resources reject readiness; resource simulation requires timed mode. Workload admission supplies its existing declared class/operation/key/tags/deadline rules and does not use finite-input metadata.

Logical inputs require null atMs; timed inputs require nonnegative time. Logical external inputs are consumed one at a time after causally generated queue drains, enabling explicit response fixtures. Timed inputs share one event scheduler. Workload fields preserve current `WorkloadDefinition`/RequestClass fields from `src/domain/execution.ts`, normalize optional profile to `{kind:'steady'}` and interval to `null`, replace `entryNodeId` with `entry:Endpoint`; workload/class IDs are UUIDs. Initial generation may only target resource entry ports. Pure logical scenarios require empty workloads/faults. Timed scenarios require at least one finite input or enabled workload. Enabled workload produces arrivals at or before its horizon, preserving retained kernel boundary semantics; explicit inputs may occur exactly at horizon if declared.

Completion union: `{kind:'quiescent'}` logical only; `{kind:'horizon',horizonMs}` timed finite observation with in-flight work visible; `{kind:'drain',arrivalHorizonMs,deadlineMs}` timed with no new exogenous generation after arrival horizon, completes when all causal work settles or returns incomplete at deadline. Logical mode rejects horizon/drain; timed mode rejects quiescent. Drain may not convert expired budget into success. The finite observation policy may pass assertions explicitly testing its remaining in-flight work. Logical mode has no elapsed-ms/throughput/utilization values.

Fault: `{id,hostId,downAtMs,upAtMs,detectionDelayMs,recoveryDetectionDelayMs,activePolicy:'fail',queuedPolicy:'reject',routeReset:'first-healthy'}`. S04 fixes the initial route reset policy; configurable alternatives need a later behavior version. Non-overlapping intervals per host, up>down. Failure/recovery and detection events precede completions at the same time only in fault-enabled scenarios. Ordinary no-fault runner ordering must remain bit-for-bit characterized. Already settled operations never settle twice; no orphan callback may occupy capacity after outage cancellation.

Boundary: `{id,source:Endpoint,schemaId,responses:[{id,match:Guard,responseFixtureId,payloadBindings:[{targetPath:Path,requestPath:Path}],delayMs:number|null,outcome:'succeeded'|'rejected'|'failed'|'expired'}]}`. Match evaluates against the request as input and empty context; the first matching unused response in declared order is consumed. Exhaustion/no match is a modeled error. Authors explicitly match business fields and may omit generated-ID comparisons; there is no implicit ignored field. Response bindings copy fields from that request into non-overlapping existing paths in a cloned schema-valid response fixture, then validate the full response. This supports explicitly echoed requestId fields without hidden injection. Logical delay null; timed delay required. Boundary ports must lie on selected scope crossings, and responses must satisfy the relevant response schema. No random implicit mock success.

Refinement: `{id,ownerElementId,memberElementIds:Id[],portMappings:[{id,outer:Endpoint,inner:Endpoint}]}`. Selection: `{refinementId,mode:'aggregate'|'refined'}`. Same-document only in v1; candidate snapshot pins content, no live external fetch. A member has at most one refinement owner; recursive containment/expansion rejects. Every crossing port has exactly one compatible mapping. Aggregate executes owner and excludes members; refined executes members and excludes owner behavior. Nested refinement is allowed only within expansion budgets and an acyclic ownership graph. Unselected visible elements stay unexecuted/uncovered.

Assertion: `{id,label,subject,operator:'equals'|'at-most'|'at-least',expected:Json}`. Subject union: `{kind:'final-state',elementId}`, `{kind:'context',elementId,path}`, `{kind:'output',port:Endpoint,path}`, `{kind:'count',scope:'root'|'message'|'element',elementId:Id|null,outcome:'generated'|'succeeded'|'rejected'|'failed'|'expired'|'inFlight'}`, `{kind:'trace-count',elementId,code}`, `{kind:'metric',elementId:Id,key:'throughput'|'meanLatencyMs'|'p95LatencyMs'|'utilization'}`. Output is ordered emitted value array; path can index it. Numeric comparison only for numeric subjects/expected values. Missing/unsupported metrics are unevaluated failures, never zero. Equality uses canonical JSON. A qualifying scenario requires >=1 assertion, >=1 consumed external input or generated workload root, and all assertions evaluated/passing. The compiler requires each assertion subject to belong to compiled scope; these conditions avoid vacuous empty runs but do not claim that author-written checks prove correctness or full coverage. Diagnostic runs may have zero assertions; badge is “Completed · no checks”, ineligible.

Assumption: `{id,key,value:Json,source:'author'|'template'|'measured',description}`. Key unique within scenario; value and source affect identity, description does not. A measured label is self-reported, not verified external measurement.

## Runner and retained-kernel interfaces

Planned public boundary (readonly data, result unions, no callbacks capable of mutating editor):

```ts
compileScenario(snapshot: AuthoredSnapshot, scenarioId: Id, signal: AbortSignal):
  Promise<{status:'ready'; manifest:ExecutionManifest; plan:{workerSessionId:Id; planId:Id}}
    | {status:'invalid'|'analysis-limit'|'cancelled'; issues:Issue[]}>
startRun(request: {runId:Id; snapshotId:string; manifest:ExecutionManifest;
  plan:{workerSessionId:Id; planId:Id}}): RunHandle
type RunControl = {kind:'pause'|'resume'|'cancel'}
interface RunHandle {
  send(control: RunControl): void;
  events: AsyncIterable<RunUpdate>;
}
```

RunUpdate is `{kind:'state',runId,state}`, `{kind:'batch',runId,firstSequence,events:TraceEvent[],metrics:MetricSample|null}`, or `{kind:'terminal',runId,status:'completed'|'invalid'|'failed'|'cancelled'|'incomplete',checks:CheckResult[],summary:RunSummary,reason:string|null}`. Exactly one terminal message; monotonically increasing sequence; stale run IDs ignored by UI but retained by their own persistence session. Pause stops work at a safe scheduler boundary, not elapsed simulation time. Cancel acknowledges and terminates worker work; Reset is cancel then clear current display, never delete saved evidence. Runtime failure carries sanitized diagnostic detail, not a modeled success/failure result. Worker serializes arrays/records only; AbortSignal remains on controller side with an explicit cancel message.

TraceEvent exact fields: `{id:string,sequence:number,rootId:string,journeyId:Id,parentId:string|null,elementId:Id,portId:Id|null,kind:'input'|'dispatch'|'queued'|'started'|'settled'|'state'|'row'|'fault'|'ignored',code:string,payloadRef:string|null,atMs:number|null,outcome:'succeeded'|'rejected'|'failed'|'expired'|null}`. IDs derive from runId plus sequence; input/root IDs derive from declared input ID or workload ID plus ordinal. Message roots have their own root ID plus parent relation to initiating user root, preserving separate conservation. PayloadRef addresses an immutable per-run content-addressed payload table. Root/journey correlation never changes retry draws.

Retained adapter must add `admit(input:ResourceInput):Admission`, `peekNext():{atMs,phase,sequence}|null`, `stepNext():KernelDelta`, `interruptHost(hostId,atMs):KernelDelta`, and `snapshot():ResourceSummary`. ResourceInput is `{rootId,journeyId,parentEventId,entryElementId,requestClassId,operation:'read'|'write',key:string|null,tags:string[],payloadRef,atMs,deadlineMs}`. Admission is `{accepted:boolean,events:TraceEvent[]}`; rejection settles once. KernelDelta is `{events:TraceEvent[],outputs:PortEmission[]}` with emission `{source:Endpoint,rootId,journeyId,parentEventId,payloadRef,outcome,atMs}`. No aggregate-only success inference is allowed. These are required new capabilities, not claims about current OpenSimulationAdapter.

One scheduler owns global time and insertion sequence for S05. Each interpreter/adapter returns emissions/scheduled work; it cannot independently advance beyond the next global event. Compare timed events by `(atMs,phase,sequence)`: phase 0 faults/detection, phase 1 retained kernel events in their original relative order, phase 2 bridge dispatch, phase 3 external input. In no-fault standalone resource runs the adapter delegates original internal tie ordering unchanged. Composition must prove same results under chunked versus one-shot stepping; no double workload generation (finite bridge input disables internal generation for that workload). Fullstack business decisions consume payload fixtures, and per-root responses drive machine events, not aggregate throughput. Fail-at-outage is a versioned new kernel capability; retained no-fault golden tests remain mandatory.

Required acceptance: S01–S05 success/failure/boundary fixtures; schema mutation and exhaustive hash vectors; malformed references; inactive incomplete elements; all scenario eligibility including zero-check diagnostics; chunk-independent scheduling; retry RNG/FIFO/cache/broker regression invariants; cancellation at compiler and runner batch boundaries. No dispatch until review resolves this contract against the retained source.

### Result records and issue vocabulary

`Issue={code:string,path:(string|number)[],entityId:Id|null,severity:'error'|'warning',message:string}`; codes are schema-owned constants, messages are display text. `CheckResult={assertionId:Id,status:'passed'|'failed'|'unevaluated'|'error',actual:Json|null,reason:string|null}`. Null actual can also be a legitimate result; status/reason distinguish unavailable.

`RunSummary={mode:'logical'|'timed',consumedInputs:number,rootCounts:Counts,messageCounts:Counts,elementMetrics:ElementMetric[],finalStates:[{elementId,stateId,context:Json}],outputs:[{port:Endpoint,values:Json[]}],coverage:{includedElementIds:Id[],excludedElementIds:Id[]},processedEvents:number,elapsedMs:number|null}`. Counts exact fields `generated,succeeded,rejected,failed,expired,inFlight`, nonnegative safe integers, conservation at roots and messages independently. Invalid inputs count as consumed inputs and explicit rejected roots. Transport and business status are distinguished by trace/check subjects; accepted business response never increments fulfillment root success twice.

`ElementMetric={elementId:Id|null,scope:'root'|'message'|'element',key:string,value:number|null,unit:'count'|'ms'|'requests/s'|'ratio',available:boolean,reason:string|null,windowStartMs:number|null,windowEndMs:number|null}`. Key is a closed catalog: generated/succeeded/rejected/failed/expired/inFlight, acknowledged, throughput, meanLatencyMs, p95LatencyMs, utilization, queued, active, cacheHits/cacheMisses/cacheEntries/cacheEvictions/cacheExpirations. Root/message rates and successful latency follow retained accounting; utilization is occupied processor time divided by slots×window duration, unavailable for non-resource/logical elements; queues/active/cache entries are instantaneous end-window gauges. Latency quantiles only over actual successful observations; no samples means unavailable, not zero. Acknowledgement is separate from completion. `MetricSample={atMs:number|null,metrics:ElementMetric[]}`; no extra key inferred by UI. Each retained catalog key must have an independent regression fixture before being exposed.

`ResourceSummary={atMs:number,rootCounts:Counts,messageCounts:Counts,metrics:ElementMetric[],pendingEvents:number,liveRoots:number}`. `RunUpdate.state` is `created|validating|running|paused`; terminal statuses are emitted only through terminal messages. Persist only terminal run rows. `AuthoredSnapshot={id:string,document:Document}`; the compiled plan is worker-local and the public plan handle is defined below.

Compilation and execution use the same dedicated worker session. CompiledPlan never crosses its boundary: the public plan value is only an opaque session/plan handle. The worker retains the validated snapshot, manifest and compiled plan; startRun verifies their IDs/hash against the handle and consumes it once. Worker restart, cancellation or release invalidates all its handles; recompile before start, never transfer an old plan to another worker. The controller translates AbortSignal to cancel messages. A plan handle cannot be imported or used as saved evidence.

Metric assertion subjects require non-null elementId and refer to that element's measurements. Root/message aggregates remain available in summaries/CSV; count subjects test global conservation. No implicit global latency/utilization aggregation is selected by null. A null metric assertion elementId is a schema error.

Pipeline row provenance is result metadata, never added to authored payload records. Each admitted list row receives `{inputEventId:string,index:number}`; transform preserves it and group-sum records the ordered union of contributing row references. `RunSummary` additionally includes `rowOutcomes:[{elementId,operationId,inputRows:[{inputEventId,index}],outcome:'emitted'|'filtered'|'duplicate'|'error',outputIndex:number|null,errorCode:string|null}]`. OutputIndex indexes that pipeline's success output array, null for non-emission outcomes. Invalid rows route their original JSON value to the error port unchanged; errorSchemaId must accept those values, and a mismatch is a failed run rather than coercion. Error details are in rowOutcomes, with closed errorCode `schema-mismatch|wrong-type|missing-path|integer-overflow`; filter and duplicate use their own outcome with null errorCode. For S03 the input/error schema declares amountMinor as scalar-union integer|string, while validate targets a record schema requiring integer. Thus r4='bad' is a valid external fixture but an explicit validation error; row labels r1–r5 correspond to input indices 0–4. This keeps row identity and diagnostics observable without an arbitrary-JSON error wrapper outside the payload grammar.

New authored fields in this appendix are executable (E); all result records including rowOutcomes are local result-only (L). Part reference descriptors must additionally remap machine responseBindings IDs/callPortId/eventPortId, pipeline input/output/errorPortId, decision inputPortId, resource entryPortId and schedule-event.eventPortId. Scenario-only input bindings are not part content.

## Common typed semantics

Payloads are validated JSON with declared scalar/record/list shapes, explicit nullability and bounded nesting. Ports name input/output direction and payload schema ID. Edge kinds: synchronous `call` (paired response/error), asynchronous `message`, and `data`; state transitions stay within a state-machine behavior. Structural `contains` and `deployed-on` are separate records. Descriptive dependency arrows do not send tokens.

Start with guards `equals`, `notEquals`, `exists`, `all`, `any` over typed field paths/literals. No coercion: missing differs from null, and string "1" differs from number 1. No user code or recursive expression references. Type errors stop validation; runtime malformed external fixture input creates an explicit modeled rejection outcome.

Each event has deterministic event ID, root/correlation ID, parent event ID, destination port, payload ref and sequence. Logical mode orders external events by declared position and internally generated events FIFO. Timed mode orders by modeled time, explicit phase priority then insertion sequence; outage/recovery phase precedes admissions at equal time, completions precede newly scheduled dispatches. The kernel's existing retry draws/attempt accounting are preserved; any change in ordering affecting them requires versioning and characterization tests.

No optional millisecond field is populated in logical mode. Event order is not elapsed time. Mixed composition uses the timed scheduler only when all time-dependent effects have declared durations; otherwise it runs logical fixtures with no latency metrics. A view's expansion/collapse never chooses a runner or refinement.

ARTIFACT reviews/2026-09-22-contract-schema-report.md
**Verdict: REVISE**

Eight concrete defects, ordered by blocking severity:

---

**D1 — Boundary request matching vs. runtime-generated request IDs** *(blocking S02, S05)*
`Boundary.requestFixtureId` uses "exact canonical request matching." But S01 and S02 embed a `request-id`-effect value in outgoing payloads — a value generated at runtime from `runId + monotonic counter`. Authors cannot pre-declare this in a authored fixture. Spec must state whether canonical matching excludes correlation/request-ID fields, or whether `requestFixtureId` matches only the business payload excluding system-generated path values. Without this, boundary fixture authors have no contract.

**D2 — `emit` effect `correlation` conflates two unrelated mechanisms** *(blocking S01 bridge)*
Two distinct correlation concepts exist: (a) the system call-frame ID, which the bridge uses to route the response back to `responseBindings.eventPortId`; (b) the authored request ID embedded in payload via `{kind:'context-request',path}`, used by the machine guard for stale-response detection. The spec defines `correlation` in the emit effect without separating these. An implementer may treat `emit.correlation` as (a), breaking bridge routing, or implement it as only (b), leaving frame tracking implicit and undefined. Spec must make the delineation explicit: call-frame ID is system-generated; the emit `correlation` field is payload-only for application-level stale detection.

**D3 — `CompiledPlan` in `startRun` is described as worker-local but passed as a parameter** *(blocking runner architecture)*
`startRun` takes `plan:CompiledPlan`. The spec then says "compiled plan is an opaque, worker-local validated plan, never portable input" and "not a structured-clone promise for Maps/functions." If compiler and runner inhabit the same worker, the parameter is fine. If they're separate workers (the spec also says "compilation runs in a worker"), the plan cannot be transferred. The required topology—one worker, two workers, structured via manifest re-compilation—is unspecified. Implementer cannot choose a worker architecture without this.

**D4 — `requestId` in response payload: authored vs. runtime-injected** *(blocking S01 schema and responseBindings compatibility check)*
"Event payload includes the response request ID as an explicit schema field." Ambiguous: does the author declare a `requestId` field in both the call-port `responseSchemaId` and the event port `schemaId` (making `responseBindings` shape compatibility check include it), or does the runtime inject it after schema validation (meaning the declared shapes can ignore it)? If authored, the compatibility check forces symmetric declaration in both schemas. If injected, the runtime violates the "no hidden field" guarantee. S01's stale-detection guard reads this field from `input`—it must be in the event schema. Spec must state which.

**D5 — `decision` behavior has no entry-port specification** *(blocking dispatch implementation)*
`pipeline` has `inputPortId`, `outputPortId`, `errorPortId`. `resource` has `entryPortId`. `machine` has `responseBindings`/event ports. `decision` has only `inputSchemaId`—no `inputPortId` or equivalent. The runtime must know which inbound port triggers decision evaluation. Nothing in the Port or Connection model identifies which port is the decision entry without an explicit field. Spec must add `inputPortId` (or equivalent) to the decision behavior record.

**D6 — Pipeline error row schema for non-validate operations is undefined** *(blocking S03 error output and S02 pipeline errors)*
`validate` errors produce "original row/provenance" to error output—the format is partially described. For `map`, `filter`, `group-sum`, `deduplicate`, and `trim`, "a non-validation operation with wrong input type produces an explicit row error." The spec never defines what fields that row error contains. The author must declare `errorSchemaId`, but without knowing what the runtime emits, the schema cannot be correctly declared. This makes fixture-based testing of error paths impossible.

**D7 — `completion` kind validation gap in logical mode** *(validator correctness)*
`{kind:'quiescent'}` is tagged "logical only." `{kind:'horizon',horizonMs}` and `{kind:'drain'}` are not explicitly prohibited in logical mode. Since logical mode has no `atMs` values, a `horizonMs` in logical mode is meaningless. Spec says "logical mode has no elapsed-ms/throughput/utilization values" but doesn't reject non-quiescent completion kinds for logical scenarios. Validation must explicitly reject them; the current text leaves a silent misconfiguration path.

**D8 — `{kind:'metric',elementId:null}` assertion subject semantics undefined**
`Assertion.subject` allows `{kind:'metric',elementId:Id|null,...}`. `{kind:'count',elementId:null}` has inferrable semantics (global root/message counts). For metric subjects, null elementId is not explained. Throughput, utilization, and latency quantiles are per-element concepts; a null aggregation is undefined. "Missing/unsupported metrics are unevaluated failures, never zero"—so null elementId metric assertions would always fail as unevaluated, which is probably not intent. Spec must either prohibit null here or define global aggregation semantics.

---

None of these require runtime code. D1 and D2 must resolve before boundary fixture authoring for S02/S05 can be specified; D3 before the runner split is decided; D4 before S01 schema authoring; D5 before decision behavior is implementable; D6 before S03 pipeline error paths can be fixture-tested. D7 and D8 are validator/assertion correctness gaps.
