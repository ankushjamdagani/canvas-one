# Current canvas traffic visuals

Read-only inventory of the playback visuals as implemented on 2026-10-05. This describes the current behavior, including known ambiguity; it does not propose a redesign.

## Storybook review

`Workspace/SimulationTraffic` now exercises the actual NodeCard and TrafficEdge with deterministic frames: outbound/return/message travel, message settlement, selected connection inventory, six individual vs seven aggregate legs, queue/processing occupancy, recent endpoint events, cycle outcomes, inspection highlighting, reduced motion and illustrative slow traversal. `UI/TrafficFlash` provides individual controls and labeled outcome examples; `Design System/Node occupancy` covers idle, processing, waiting, mixed occupancy and backlog.

Browser review exposed an existing packet-position defect: spreading SVG DOMPoint omitted its inherited x/y getters. `placeLeg` now reads x/y explicitly, verified against actual browser SVG geometry for both directions. This is a positioning correction, not a new visual language. The remaining ambiguities below are unchanged.

## Data path and temporal behavior

- `usePlaybackTraffic` reads `PlaybackStore.stateAt(playheadMs)` every animation frame, groups active legs by connection and flashes by connection or element, and publishes `prefers-reduced-motion` state. It resets to empty when the source disappears. (`src/features/workspace/usePlaybackTraffic.tsx:23-69`)
- A leg exists from a `sent` or `response` record until its recorded `arriveAtMs`; progress is linear simulated-time interpolation from departure to arrival. `sent` is `out`; `response` is `back`. (`src/features/runs/playback.ts:408-435`; `src/features/runs/playback.ts:33-40`)
- Typical simulated transport latency is 2 ms in the current model, while event flashes remain visible for 240 simulated ms. A flash therefore lasts about 120 times longer than a typical leg and can outlive traversal substantially. (`specs/revamp/decisions.md` D49; `src/features/runs/playback-flashes.ts:3-4`)
- Individual legs appear as teal rounded rectangles with a chevron. Outbound progresses source-to-target; return uses `1-progress`, and its marker rotates 180 degrees. Keys appear only in the selected-edge detail list. (`src/features/workspace/TrafficEdge.tsx:252-310`; `src/features/workspace/playbackTraffic.ts:13-37`)
- Reduced motion freezes individual marker positions at evenly spaced static points on the edge; return markers retain their reverse heading. Aggregate edge animation stops entirely. Flash icons remain fully opaque instead of fading. (`src/features/workspace/playbackTraffic.ts:13-37`; `src/features/workspace/TrafficEdge.tsx:166-176`; `src/components/ui/traffic-flash.tsx:17-31`)
- Pause freezes individual packet positions, occupancy and flash age at the playhead. Seeking reconstructs those facts at the chosen recorded instant; playback speed changes their real-time visibility because flash lifetime is measured in simulated time. Aggregate CSS dash motion is the exception described below.

## Connection states

- **0–6 active legs:** show one marker per leg, irrespective of direction. Markers are positioned on the actual edge path at the playhead. There is no direction-specific color; direction is communicated by chevron orientation/trajectory and `data-direction`. (`src/features/workspace/playbackTraffic.ts:3-11`; `src/features/workspace/TrafficEdge.tsx:190-207,252-310`; `src/features/workspace/playbackTraffic.test.ts:53-72`)
- **7+ active legs:** replace every individual marker with parallel dashed strokes: outbound is offset −3 px and runs normally, return is offset +3 px and runs in reverse. The shared teal strokes have opacity .6. Their dash length grows with count (capped at 12) and animation period shrinks with load (minimum .15 s). A midpoint chip reports total `in flight · out / back`. The strokes do not encode each request's position or identity. (`src/features/workspace/playbackTraffic.ts:3-11`; `src/features/workspace/TrafficEdge.tsx:160-189`)
- Aggregate dash animation runs independently of the simulated playhead: it continues while playback is paused or complete if the paused playhead still has at least seven legs on that edge. (`src/features/workspace/TrafficEdge.tsx:171-177`; `src/features/workspace/usePlaybackTraffic.tsx:31-67`)
- Selecting an edge after a run adds a scrollable “Units in transit” panel with count and keys/directions; it is an inventory, not a cycle-to-marker mapping. (`src/features/workspace/TrafficEdge.tsx:209-239`)
- **Async/message travel:** message `sent` records use the same outbound markers/aggregation. A `settled` message record may add an outcome badge at the connection's source side (progress 0), even though settling normally describes work at the receiving node. There is no separate visual grammar for messages, broker delivery, retries, or child-message lineage on the edge. (`src/features/runs/playback.ts:138-171`; `src/features/workspace/TrafficEdge.tsx:123-141`)

## Node states and event flashes

- Queued and processing flow facts produce exact per-element counts. A card below the node says “N queued” with a queue bar of width `100*N/(N+6)%`, plus “N active” in a circular count. Zero/zero hides the panel. The bar is intentionally compressed and has no capacity meaning. (`src/features/runs/playback.ts:529-548`; `src/components/ui/node-occupancy.tsx:1-38`)
- `queued` and `processing` are visually represented as counts only; there is no distinct processing animation, waiting age, service progress, saturation/capacity scale, or per-request queue identity. Failures are not reflected in occupancy. (`src/features/runs/playback.ts:408-435`; `src/components/ui/node-occupancy.tsx:1-38`)
- Lifecycle facts create short badges grouped by connection/node, kind, progress, and outcome. The flash window is 240 simulated ms; same-group facts inside that recent window combine into a count and use the newest constituent age. That count means recent flash events, not current in-flight work. Normal motion expands/fades a sent ring and fades all badges; reduced motion fixes opacity and uses a fixed 7 px sent ring. (`src/features/runs/playback-flashes.ts:3-77`; `src/components/ui/traffic-flash.tsx:1-70`)
- A departure shows an expanding ring at the source; a confirmed arrival shows a check at the destination. Return departure is located at the destination end; return arrival/check is at the source end. These are endpoint glyphs around the line, not markers traveling along it. (`src/features/runs/playback.ts:138-168`; `src/features/workspace/TrafficEdge.tsx:123-158`)
- Outcome glyph/color mapping: `ok` green check; `failed` and `lost` risk-colored X (lost uses dashed diamond); `rejected`, `expired`, `timed-out` clay colored slash, hourglass, or clock; `stuck` purple square with horizontal bar. Response outcomes appear near the caller/source side. A lost outbound send gets a lost glyph at path midpoint. A response with `arriveAtMs: null` gets no lost/outcome glyph through this construction path, so loss on the return leg is not visibly represented here. (`src/components/ui/traffic-flash.tsx:3-15,32-67`; `src/features/runs/playback.ts:160-170`)
- A completed workload cycle with an outcome flashes that outcome over the workload-entry element. Thus some outcome badges belong to the ingress node, while connection outcome badges describe a transport/edge event; the UI does not explain this scope distinction. (`src/features/runs/playback.ts:198-214`)

## Inspection highlight and limits

- Selecting a lifecycle event in Cycle Inspection seeks the playhead to that event and sends it to Workspace. The recorded event's element gets a ring; its recorded connection gets a 4 px primary path highlight and both recorded endpoints get node rings. The connection path is highlighted only if the current connection still has the same endpoints. It is a persistent selected-event highlight, not a transient playback pulse; clearing/resetting the selected event removes it. (`src/features/runs/CycleInspection.tsx:95-103`; `src/features/workspace/Workspace.tsx:1236-1253`; `src/features/workspace/TrafficEdge.tsx:121`; `src/features/workspace/NodeCard.tsx:50-56`)
- The highlight adds to ordinary playback markers, occupancy, and flashes, so several encodings can overlap at once. It highlights event endpoints rather than a full request journey; selecting one event does not highlight all other connections/nodes in the cycle. Direct-at-node events have no edge to highlight. If architecture endpoints changed since recording, the old edge is intentionally not highlighted, although known recorded node IDs may still ring. (`src/features/workspace/Workspace.tsx:1243-1253`)

## Ambiguities visible in the current behavior

- “Out/back” means request leg vs response leg for call traffic, but for message traffic only outbound message travel is normally shown; it is not a universal client-to-server direction label.
- Teal individual markers and parallel teal dashes show movement/load, while status colors are reserved for transient outcome glyphs. There is no persistent indication that a request is waiting, processing, retrying, rejected, or failed after the 240 ms flash expires.
- The >6 transition swaps position/identity markers for moving density strokes; at the threshold, exact traversal becomes aggregate volume. The count chip says all legs in flight but does not show where along the connection they are.
- Node occupancy counts are aggregate per element across traffic, with queued and active categories but no explanation of how they relate to edge markers or flashes. A request can therefore appear at an edge and, after arrival, as occupancy/flash at a node according to separate record facts.
- Return arrows are inferred from `response` phase and reversed geometry, rather than explicit connection topology. The smoothstep path's visual source/target positions can make out/back routing hard to parse in dense diagrams.
- Flashes at a shared endpoint are stacked by array order and only lightly offset; grouping/counting reduces but does not eliminate collisions in dense traffic. Because a flash lasts around 120 typical transport durations, multiple endpoint glyphs can coexist after their corresponding packets have arrived.
